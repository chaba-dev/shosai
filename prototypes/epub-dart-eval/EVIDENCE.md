# Phase C evidence — Dart EPUB vertical slice

Scope: the evaluation prototype in this directory. Measurements come from one
runner (`framework16`, Linux, software rasterization under Xvfb). Nothing here
is a production baseline, an architecture decision, or a claim of parity with
the Rust renderer.

## Reproduction

```sh
# fixtures (byte-identical check)
.agents/dev bash -lc 'cd prototypes/epub-dart-eval && python3 tool/generate_fixtures.py --check'

# correctness evidence
.agents/dev bash -lc 'cd prototypes/epub-dart-eval && flutter test'
.agents/dev bash -lc 'cd prototypes/epub-dart-eval/packages/shosai_epub && dart test'

# measurements (release bundle + Xvfb; writes artifacts/measurements/*.json)
.agents/dev bash -lc 'cd prototypes/epub-dart-eval && \
  SHOSAI_MEASURE_TRIALS=5 \
  SHOSAI_MEASURE_BOOKS="$PWD/fixtures/rich-chapter.epub,$PWD/fixtures/long-chapter.epub,$PWD/fixtures/long-chapter-stress.epub" \
  SHOSAI_MEASURE_SPINES=0,1,0 bash tool/measure.sh'

# eager/progressive comparison (one strategy per run, same fixtures)
.agents/dev bash -lc 'cd prototypes/epub-dart-eval && \
  SHOSAI_MEASURE_TRIALS=3 \
  SHOSAI_MEASURE_BOOKS="$PWD/fixtures/rich-chapter.epub,$PWD/fixtures/long-chapter.epub,$PWD/fixtures/long-chapter-stress.epub,$PWD/fixtures/huge-paragraph.epub" \
  SHOSAI_MEASURE_SPINES=0,1,0,0 \
  SHOSAI_MEASURE_LAYOUT=eager \
  SHOSAI_MEASURE_OUT=$PWD/artifacts/measurements/eager.json bash tool/measure.sh'
```

## Cross-check against the Rust implementation

`packages/shosai_epub/test/normalize_test.dart` ports production Rust assertions
from `crates/shosai-core/src/epub/render.rs` and
`crates/shosai-core/tests/epub_conformance_tests.rs`:

- canonical text for headings, lists and tables (`Quarter\tValue`,
  `First half\tQ1 link`, `Q2 chart`);
- anchor offsets for sections, inline spans, duplicate ids, empty markers,
  captions, rows and cells;
- MathML fallback strings (`root(x, 3)`, `x_1^2`, `π`, no `\pi`);
- rejection fixtures: malformed chapter markup, oversized SVG dimensions,
  duplicate archive entries;
- image alt handling (block-level alt is canonical; inline alt is not).

One ported case is asserted as a **deliberate deviation**: display-block MathML
inside a paragraph is not promoted, so its generated separators are absent
(`before (a)/(b) after tail` vs the Rust `before \n(a)/(b)\n after tail`).
Rust can have bugs; these tests reuse Rust's *expectations*, not its code.

What the coverage checks do **not** establish: they compare the flow's own line

## Measurements (release bundle, Xvfb, llvmpipe)

Pre-progressive baseline: `artifacts/measurements/measure-20260928T080623Z.json`
— one complete run with the eager strategy, 5 trials per book, report written
after every completed book. Each book is measured with a fresh in-memory
position store, so repeated runs start at the same place; the report records
`initial_spine`/`initial_scalar` per book.

The window geometry of this earlier session differs from the follow-up runs
below (fewer lines per page), so its absolute numbers are not comparable with
the eager/progressive table; the follow-up section is the like-for-like
comparison.

Frame-timestamp latencies from the first harness revision were **not** usable as
presentation measurements (the engine's stored begin-frame timestamp is not a
completion or presentation clock, and one sample even reported less frame
latency than layout work). The harness reports two honest endpoints:
`state_latency_micros` (dispatch → the model state the operation produces) and
`verified_capture_micros` (dispatch → a content-verified capture, including the
capture round-trip). Neither is a physical-presentation measurement; the capture
endpoint is an upper bound whose additional latency beyond the state endpoint
comes from the verification path: a fixed 120 ms pump wait, the `toImage`
render, the ink analysis, and (when an output path is set) a PNG encode. For
warm navigation most of the ~200 ms figure is that path; for a cold open the
layout dominates instead. The capture endpoint is not comparable across
operations.

| --- | ---: | --- | --- | --- | --- | --- |
| rich-chapter (0) | 729 | 1 spread / 26 / 34 | 363 ms / 586 ms | 3.6–4.6 ms (chapter transition; single spread) | 106–116 ms / 2.8–18.1 ms | 106 ms |

Content verification passed at every measured point (ink present in the

`long-chapter` opens on its small first chapter, so its cold-open numbers

An earlier run mixed layout-work values from a pre-font-plumbing revision with
newer state latencies (producing an impossible "132 ms including coalescing,
215 ms of layout work" pair); that table was superseded by the single-run table
above, and the older logs remain under `.amp/in/artifacts/epub-dart-eval/` as
the historical record. The current runs also use a fresh in-memory position

Resident memory (MiB). `ProcessInfo.currentRss` is current resident memory and
`ProcessInfo.maxRss` is the process peak; neither is a retained-heap measurement
and no causal attribution to specific structures is claimed.

| Book | After first content | After navigation | Continuous mode | Peak (max RSS) |
| --- | ---: | ---: | ---: | ---: |
| rich-chapter | 256 MiB | 256 MiB | 268 MiB | 310 MiB |
| long-chapter (102,977 scalars) | 272 MiB | 294 MiB | 309 MiB | 365 MiB |
| long-chapter-stress (606,227 scalars) | 386 MiB | 389 MiB | 480 MiB | 539 MiB |

Interpretation, stated conservatively:

- Warm page turns are cheap because the chapter flow and its page composition
  are precomputed once per layout.
- Relayout is the dominant cost and it is UI-thread work: tens of milliseconds
  of layout computation for a 103k-scalar chapter and roughly half a second for
  the 606k stress case in this environment. The Rust baseline's relayout budgets
  (18–22 ms p50 for a 16-chapter generated book) are not comparable: different
  machine, different fixture size, and the Rust numbers are Iced event-loop
  measurements. What is comparable is that Dart text layout cannot be moved off
  the UI thread (dart:ui is UI-thread bound), so a large relayout is a visible
  stall unless work is chunked or cached.
- Continuous mode's RSS snapshot is higher than the post-navigation snapshot
  (long: 294 MiB → 309 MiB, +4.9 %; stress: 389 MiB → 480 MiB, +23.2 %), but
  five font-size relayouts run between those two samples and there is no
  immediately-before-switch sample, so this run cannot attribute the growth to
  continuous mode. These RSS snapshots do not identify which allocations
  account for the growth or establish retained-heap growth. This remains an
  unresolved bounded-rendering concern (see "Open questions").
- The absolute numbers are software-rasterization numbers on one runner; they
  establish ordering and shape, not desktop-GPU budgets.

## Progressive layout: eager vs progressive (same session)

Follow-up experiment. Both strategies ran back-to-back on the same fixtures in
one session (`artifacts/measurements/eager.json`, `progressive.json`; release
bundle under Xvfb, 3 trials, `SHOSAI_MEASURE_LAYOUT=eager|progressive`). The two
runs report the same page and line counts; the strategies produce the same
layouts, which committed equivalence tests check range by range (the progressive
flow is compared block-for-block against the eager flow, and the line-boundary
fast path against the logical boundary API). What differs is *when* the layout
is installed and how the work is spread. Sample counts differ per row: cold open, spine jump, mode switch and the
distant reopen each have one sample per run; the relayout rows are the *first*
font change of their kind (a cache miss for progressive) and the table below
lists the later cached repeats; navigation has three samples (not tabulated).

Endpoints per operation: `usable` = dispatch → the model state that renders the
requested location; `complete` = dispatch → every node measured (equal to usable
for eager); `longest block` = the longest event-loop timer gap while the
operation ran. The probe is a 2 ms periodic timer: a blocking synchronous call
delays the tick, so the longest gap approximates the longest uninterrupted
UI-thread work interval. It is not a presented-frame measurement (the harness
runs headless and does not drive vsync), and an inter-tick gap can include idle
time or several tasks, so it is not a strict lower bound on one task. Idle
calibration on this runner is ~4 ms (the rich book's calibration window includes
app startup, ~32 ms).

What the experiment shows:

- **Visible-location-first works where the chapter is large.** The 606k-scalar
  chapter is usable in 120 ms instead of 300 ms and its longest UI-thread block
  drops from 173 ms to 24 ms; the 103k-scalar chapter's spine jump is usable in
  6 ms instead of 35 ms.
- **A new session at a distant position is the strongest case.** Reopening at
  85 % of the 606k chapter is usable in 123 ms instead of 298 ms, while the
  background fill finishes at 441 ms.
- **Reuse removes relayout work entirely**: every cached repeat reports
  `layout_work_micros == 0` (its time is the 80 ms coalescing delay plus the
  install), while the eager repeats of the same changes still measure the
  chapter (longest blocks 22–184 ms).
- **Cancellation is bounded**: the longest block during a four-intent burst is
  20–51 ms (progressive) versus 25–198 ms (eager).
- **Windowing costs little when it cannot help.** The 729-scalar rich chapter
  fits the first window, so progressive and eager are within tens of
  milliseconds of each other (window install plus snapshot and pagination), and
  in this run progressive's cold open was the faster of the two.

### A single huge paragraph is no longer a stall

The 120k-scalar single-paragraph fixture initially took ~1.09 s to usable in
both strategies with a ~990 ms longest block. Profiling (debug/JIT, 120k
characters, 3,935 lines) separated the costs:

| Stage | Time |
| --- | ---: |
| `TextPainter.layout()` (shaping) | 29 ms |
| `computeLineMetrics()` | 7 ms |
| per-line `getLineBoundary` calls (7,870 calls) | 1,124 ms |
| per-boundary canonical mapping (`canonicalAt`) | 1,533 ms |
| full chapter flow (before the fix) | 2,679 ms |

The stall was the prototype's own per-line loops, not Flutter shaping: the
engine's line-boundary call scans the paragraph, so calling it once per line is
quadratic in the paragraph length, and the canonical mapping recounted scalars
from the span start for every boundary. Both were fixed:

- line starts for left-to-right blocks without bidi content come from one
  vertical caret probe per line (16 ms for 3,935 lines, 68× cheaper); blocks
  with right-to-left or bidi-control content keep the logical boundary API, and
  an equivalence check over every paragraph of the long chapter and the huge
  fixture reports 0 range mismatches between the two paths;
- all boundaries of a block map to canonical scalars in one monotone pass.

After the fix the same fixture lays out in **56 ms** in the same debug profile
(48× faster), and the release harness reports ~164–177 ms to usable with a
41–45 ms longest block for the whole book (eager and progressive). The
paragraph is still one indivisible shaping call, but that call is ~29 ms debug
(and the fixture's 30 pages are unaffected in content: the exactly-once
coverage test for this fixture passes against the independent expectation).
Fragmenting oversized paragraphs is therefore no longer needed for this
fixture size; it remains the option if a paragraph is orders of magnitude
larger.

Resident memory (MiB). The progressive runs install a bounded layout cache
(default 2 entries), so their snapshots can differ; these samples cannot
attribute the difference to the cache:

| Book | eager after first content | progressive after first content | eager at the dispose sample | progressive at the dispose sample |
| --- | ---: | ---: | ---: | ---: |
| rich-chapter | 255 | 256 | 278 | 274 |
| long-chapter | 273 | 273 | 352 | 374 |
| long-chapter-stress | 394 | 394 | 622 | 636 |

while the disposed controller, its model and its cache are still reachable (the

count (`SHOSAI_MEASURE_LAYOUT_CACHE`, default 2), not by bytes.

Honest limits of this experiment:

- The probe measures event-loop gaps, not presented frames; absolute values are
  one runner under software rasterization.
- While a chapter is incomplete the page ordinal is window-local and the footer
  reports durable progress ("Laying out — N%") instead of a page total; the
  total becomes the chapter's once the fill reaches the chapter start. No total
  is fabricated.
- The distant-position and cold-open numbers include the app's open effect
  (file read, font registration, image decode) in both strategies; the
  strategies differ only in the layout phase.
- The absolute page and line counts differ between sessions (the harness window
  geometry differs), so the eager/progressive comparison is only valid within
  one session's pair of runs; both runs above agree with each other.

Inspected defects found and fixed during this work (kept as evidence that the
captures are load-bearing):

1. Table captions were painted twice (once by the caption slice, once by the row
   slice). Fixed by painting the caption only in its own slice.
2. Code blocks, math fallbacks and image alt text were mapped to canonical 0
   because their synthetic spans carried no canonical range; page starts and
   reopen positions were wrong. Fixed with node-derived canonical ranges.
3. Continuous mode painted a live background behind text painted with the
   previous palette, producing dark-on-dark after a theme change. Fixed by
   baking the palette into the layout.
4. A `RepaintBoundary` sized to the whole continuous flow was replaced by a
   viewport-sized painter overlay.
5. The generated PNG fixture had a corrupt IDAT CRC; the generator now builds
   the PNG itself.
6. A font-size/theme/viewport intent did not invalidate an already-running
   layout: the superseded completion could install a stale layout, clear
   `relayoutPending`, and let a readiness check pass on it. Fixed by bumping the
   layout revision at intent time (`controller.dart`), with a regression test
   that compares each settled layout's measured font size against the final one.
7. A nested table inside a cell rendered a rebuilt string (`A\\tB`) while its
   span claimed the node's canonical range (`A\\n\\tB`), so a hit on `B`
   addressed the separator. Fixed by rendering the exact canonical substring
   (trailing generated newlines trimmed with the range), with a hit-test
   regression on the glyph's own box.
8. A delayed clipboard completion cleared a newer selection. Fixed by only
   clearing the selection the copy was started from, with a delayed-clipboard
   regression test.
9. The measurement report failed to encode because a warm-navigation sample
   stored a Dart record instead of scalar fields; the last two runs produced
   only logs. Fixed, and `measure.sh` now passes `SHOSAI_MEASURE_SPINES`
   through. A later review also found the evidence table mixed layout-work
   values from a different revision; the table above is now generated from one
   complete run.
10. Code spans painted as filled black boxes in test captures: `flutter_test`
   has no platform monospace face, so the reader's `monospace` family fell back
   to the Ahem placeholder. Fixed by registering the platform monospace TTF as
   `monospace` in the test font loader; the release capture rendered code
   correctly all along, and typography claims use that output.
11. A superseded progressive driver cleared the *newest* driver's active
   session when it noticed it was stale, so on-demand range extension silently
   stopped working after a jump. Fixed by clearing the active session only when
   it still belongs to the same request; the navigation test covers it.
12. A font-size intent computed the page geometry with the previous font size,
   so a page height for the old typography was used until the next intent.
   Fixed to compute geometry from the new typography.
13. The layout cache was keyed by internal resource paths and survived document
   replacement, so opening a second book that shares those paths could install
   the first book's measured blocks (and blocks referencing disposed images).
   Fixed by scoping the cache to one document lifetime; regression test opens
   two fixtures that both use `OEBPS/Text/chapter-1.xhtml`.
14. `_installLayout` clamped the durable scalar to the *rendered* range, so a
   valid chapter-end position (after the last rendered glyph, before the
   canonical stream's trailing separator) moved backwards. Fixed to clamp to
   the chapter only; regression test jumps and reopens at `scalarCount`.
15. Layout of a very long paragraph was quadratic: the engine's per-line
   boundary call scans the paragraph and the canonical mapping recounted scalars
   from the span start, so a 120k-scalar paragraph stalled ~1 s in release (the
   shaping call itself is ~29 ms). Fixed with a vertical caret probe per line
   for left-to-right blocks without bidi content (the logical boundary API is
   kept for bidi) and one monotone canonical mapping pass; a debug profile of
   the same fixture dropped from 2.68 s to 56 ms, and the release harness from
   ~1.09 s to ~0.17 s to usable.

### Continuous-scroll extent correction (investigated, partly reproduced)

A review raised a failure mode for continuous mode: a programmatic scroll target
beyond the scrollable extent is corrected by the scroll surface's physics, and
those correction notifications reach the controller as if they were navigation.
The investigation reproduced the **mechanism** but not the end-to-end failure:

- Forcing the scroll position out of range directly (`jumpTo(maxScrollExtent +
  300)`) in a widget test does correct back and does notify: 72
  `EpubReaderContinuousOffsetChanged` messages were dispatched and the durable
  scalar moved from the chapter end (729) to 474, and was persisted. The
  mechanism is real.
- With the published guards, a chapter-end position in continuous mode installs
  an offset equal to the reachable extent (`flow.height - viewportHeight`), so
  the surface has nothing to correct: `flow.height = 1578`, viewport `591`,
  `maxScrollExtent = 987`, model offset `987`, scalar `729`. Reverting the
  guards and shrinking the reported viewport did **not** reproduce the
  end-to-end failure in a widget test (the view re-reports its real viewport
  before a correction can propagate).

Disposition: the guards (controller clamps the installed offset to the
reachable extent; the view jumps to the reachable extent and records the
programmed value) are kept and are described as **precautionary** — they remove
the one path that was hypothesized, but the end-to-end failure is unproven, and
a correction from any other source of an out-of-range position would still be
reported as navigation. A suppression of programmatic-correction feedback was
drafted and rejected for this increment because no discriminating regression
could be written for it.

## Open questions this slice does not resolve

- **Retained-heap attribution.** RSS is not retained memory. A VM-service heap
  profile or a separate isolate is needed to say whether the continuous-mode and
  stress-case growth is retained layout or another allocation.
- **Physical presentation timing.** No presented-frame measurement was made; the
  harness reports state-change and verified-capture endpoints only.
- **Canonical-stream parity.** The MathML block-promotion deviation means the
  canonical stream is not yet identical to the Rust `search_text()` order for
  that case. This is recorded as an incomplete gate, not as a passing one.
- **Over-tall table rows.** Placed clipped and counted, not split at line
  boundaries. The Rust implementation splits rows; the prototype does not.
- **Layout on the UI thread.** No isolate strategy exists for `dart:ui` text
  layout. A hybrid (Rust normalization + Flutter layout) does not remove this;
  it only moves normalization off the UI thread.
- **Real-world CSS.** Only the fixture corpus and one generated rich chapter
  were exercised; no licensed book corpus was read.
- **Fonts.** WOFF/WOFF2 and emoji are unsupported; Hebrew/Arabic needed
  prototype-only host faces.
