#+TITLE: RFD 0004 implementation checklist
#+STARTUP: showall

Implements [[file:README.adoc][RFD 4: Mobile support]].

* Purpose

Determine whether Shōsai should ship a mobile companion or a full mobile reader,
then build the smallest viable product without coupling shared reading data to a
desktop UI or local filesystem layout.  This is a gated plan, not a claim that
the current desktop application already runs on mobile.

** Goals

- Make an evidence-based product and platform decision before implementation.
- Reuse format, identity, storage, and sync logic through a platform-neutral core.
- Deliver mobile-appropriate navigation, lifecycle handling, accessibility,
  secure storage, and packaging for the selected platform scope.
- Preserve desktop behavior while removing only the core assumptions that block
  portable identity and storage.

** Constraints and non-goals

- The existing frontend is a desktop Iced application concentrated in
  ~crates/shosai-app/src/app.rs~.  Its ~rfd~ dialogs, filesystem paths, window
  behavior, keyboard shortcuts, and PDFium loading must be treated as desktop
  integrations, not mobile-ready abstractions.
- Current library, reading state, and bookmarks use canonical local file paths as
  identity.  Mobile work cannot synchronize or relocate those records safely
  until portable identity exists.
- A companion (catalog/progress/bookmark) app and a full PDF/EPUB/CBZ reader are
  different products.  Scope must not silently expand from one to the other.
- Rewriting the desktop UI, hosting a cloud service, DRM support, store billing,
  and background transfer of full book files are non-goals for the first release.
- Do not promise both Android and iOS simultaneously.  Select a first platform
  after feasibility evidence and account for store/toolchain access.

* Repository Baseline and Dependencies

- ~crates/shosai-core/src/library.rs~, ~reading_state.rs~, and ~bookmarks.rs~ own
  useful domain and SQLite APIs, but records are tied to canonical paths.
- SQLite schema lives in ~crates/shosai-core/migrations/~; migrations 001–005
  contain library, preferences, bookmarks, and EPUB locations.
- Format code is under ~crates/shosai-core/src/pdf.rs~, ~cbz.rs~, and ~epub/~.
  Each dependency must be compiled and exercised on the target; being in
  ~shosai-core~ does not by itself make it portable.
- ~crates/shosai-app/src/main.rs~ launches Iced and ~app.rs~ contains desktop UI,
  storage setup, settings, tests, and ~rfd~ open/import dialogs.

** Dependency on cloud sync and portable storage

- A companion app requires the stable content/book IDs, sync-ready records,
  tombstones, deterministic merge, transport, and credential model described in
  [[file:../0003/README.adoc][RFD 3: Cloud synchronization]] through its usable
  end-to-end sync milestone.
- A full reader may prototype local opening before remote sync is complete, but
  release still requires portable IDs so imported mobile content can associate
  with desktop records.
- Mobile databases need a platform-provided application-data location and safe
  lifecycle-aware access.  A content URI, security-scoped URL, or sandbox token
  is a local locator, never the portable book ID.
- If book-file transfer is later required, create a separate encrypted content
  transfer plan; metadata sync must not accidentally become file sync.

* Gate 0 — Product and Platform Feasibility

No production mobile frontend starts until this gate records a decision.

** Product questions and prototypes

- [ ] Define target users and top workflows for two explicit candidates:
  - *Companion*: browse synced library metadata, inspect/update progress, manage
    bookmarks/notes, and trigger sync; no local document rendering.
  - *Full reader*: import/open permitted local documents and read PDF, EPUB, and
    CBZ with resumable position and bookmarks.
- [ ] Validate demand and minimum offline behavior for each candidate.
- [ ] Produce interaction sketches for touch navigation, bookmark editing,
  import/open, sync errors, and compact/rotated screens.
- [ ] Select one candidate and one first platform with measurable rationale.

** Flutter and platform viability spike

- [ ] Build the Flutter vertical slice proposed by RFD 4 on physical Android and
  iOS devices.  Verify startup, touch/gesture events, text input, accessibility,
  suspend/resume, orientation, safe areas, high-DPI scaling, memory pressure,
  and renderer recovery.
- [ ] Have the spike read/write SQLite in the app sandbox, resume after process
  death, and call one shared-core API through the packaged Dart/Rust bridge.
- [ ] For a full reader, separately prove PDFium binary build/loading and page
  render, EPUB text/image rendering, and CBZ image decoding under memory pressure.
- [ ] Verify platform document pickers and persisted access grants; do not use
  ~rfd~ as the mobile design.
- [ ] Verify TLS/networking, secure credential storage, background execution
  limits, cross-compilation, signing, and install packaging.
- [ ] Confirm or revise RFD 4 from measured accessibility, lifecycle,
  maintenance, binary-size, rendering, and testability evidence.

*Gate acceptance*: a reproducible physical-device spike and published RFD choose
companion or full reader, first platform, frontend technology, and supported
formats.  If Flutter fails required criteria, retain the shared Rust core and
choose native mobile frontends or stop; do not patch around the gate by asserting
desktop readiness.

* Architecture Decisions Required

** Product/platform ADR

Record companion versus full reader, Android versus iOS first, minimum OS,
tablet/phone scope, offline contract, and explicit deferred features.

** Frontend boundary

Confirm the Iced desktop and Flutter mobile split in RFD 4 from Gate 0 evidence.
Define the core boundary as commands/data/errors rather than Iced messages,
Flutter widgets, or platform locators.  Select a Dart FFI-compatible bridge and
specify ownership, thread affinity, error mapping, async progress, cancellation,
and buffer release.  No Rust panic or borrowed reference crosses FFI, and the
bridge must not require per-widget, per-glyph, or per-frame calls.

** Portable identity and locator ADR

Adopt the cloud-sync identity decision.  Model local files as platform locators
with permission state and potentially expiring access.  Specify reauthorization,
changed content, duplicate imports, and unavailable files.

** Storage and lifecycle ADR

Decide database location, connection ownership, migration timing, backup flags,
encryption requirements, suspend/process-death behavior, and version downgrade.
Database work must not require a running desktop window or a ~Path~ for every
synced record.

** Document-rendering ADR (full reader only)

Decide supported formats per platform based on measured binary size, native
dependencies, memory, rendering latency, licensing, and store policy.  Define
cache limits and cancellation; PDFium desktop success is not mobile evidence.
For EPUB, choose between a shared renderer-neutral Rust layout/scene and Flutter
layout of the shared semantic model.  Preserve search offsets, links, bookmarks,
pagination, themes, resource limits, and readable fallback behavior without a
second parser or resource-security policy.

* Shared Core Versus Frontend and Packaging

** Shared core responsibilities

- Stable content/book and record IDs; library, progress, bookmark, tombstone, and
  deterministic merge models.
- Versioned SQLite migrations and transactional repositories.
- Transport-independent sync orchestration and payload validation.
- Format parsing/rendering only for dependencies proven on the selected target.
- Pure tests and compatibility fixtures shared with desktop.

** Mobile frontend/platform responsibilities

- Flutter application lifecycle, navigation, adaptive phone/tablet layouts,
  gestures, accessibility, safe areas, and platform error presentation.
- Document picker/security-scoped access/content URI grants and local locators.
- Secure credential APIs, networking/background scheduling adapters, and OS
  privacy controls.
- Renderer surface integration, memory-warning response, signing, entitlements,
  store metadata, and packaging.

The desktop ~shosai-app~ remains a desktop frontend.  Share behavior by moving
well-defined domain operations into core, not by importing ~app.rs~ into mobile.

* Likely Files and Modules

- Extend ~crates/shosai-core/src/library.rs~, ~reading_state.rs~,
  ~bookmarks.rs~, and ~lib.rs~ for portable APIs.
- Reuse/add the identity and ~sync/~ modules and migrations planned by
  [[file:../0003/README.adoc][RFD 3]].
- Audit ~crates/shosai-core/src/pdf.rs~, ~cbz.rs~, ~epub/~, and their dependencies
  under target-specific builds and tests.
- Update ~crates/shosai-app/src/app.rs~ only to consume shared abstractions and
  preserve desktop behavior; keep ~rfd~ in the desktop integration.
- Add a Flutter mobile project and Rust bridge only after Gate 0 passes; its name,
  generator, and layout remain outputs of the measured frontend boundary.
- Add target build/package definitions in workspace and CI files only in M4.

* Migration and Compatibility Strategy

- Follow cloud sync's additive migration and dual-read/write period.  Never edit
  released migrations 001–005 or fork a mobile-only logical schema.
- Keep schema/protocol fixtures that prove desktop and mobile versions can sync
  across the declared compatibility window.
- Run migrations before exposing UI, in a cancellable/recoverable startup flow;
  retain enough information to diagnose failure without logging private data.
- Store platform locators in device-local tables/columns and exclude them from
  sync payloads.  Reauthorization changes a locator, not the stable book ID.
- A newer incompatible database or wire version must fail safely without writes.
  Publish minimum compatible desktop/mobile versions before rollout.
- Uninstall, sign-out, unlink, remote deletion, and OS backup/restore have distinct
  documented effects on local files, SQLite records, credentials, and tombstones.

* Verification and Acceptance Criteria

** Common

- Gate 0 evidence exists for physical devices; chosen scope, platform, frontend,
  and formats are explicit.
- Existing desktop library/open/import/reading/bookmark tests continue to pass.
- Shared core builds for selected target(s), has no Iced/~rfd~ types in its public
  domain API, and uses stable IDs rather than paths for synchronized records.
- Desktop and mobile converge for progress, EPUB offsets, bookmarks/notes, and
  deletes after offline concurrent changes and duplicated/out-of-order delivery.
- Upgrade, process death, revoked file access, no network, low storage, invalid
  payload, and invalid credentials leave the database usable and errors actionable.
- Accessibility audit covers screen reader, text scaling, contrast, touch target
  size, focus order, and orientation on the supported device matrix.
- Credentials are in approved secure storage and logs/crash diagnostics contain
  no secrets, note text, or raw reading history.

** Companion-specific

- Users can view synced library metadata and progress, edit bookmarks/notes, see
  sync state, work offline, and intentionally unlink/delete local app data.
- No UI or documentation implies that document files can be opened locally.

** Full-reader-specific

- Platform picker access survives restart where the OS permits and revoked access
  has a recovery flow.
- Every promised format opens representative, large, and malformed fixtures
  within documented startup, memory, and interaction budgets on physical devices.
- Position and bookmark restore remain correct after rotation, suspension, process
  death, file move/reselection, and content replacement.
- Packaging includes and legally documents required native libraries such as
  PDFium for every selected architecture.

* Security and Privacy Risks

| Risk | Required mitigation |
|------|---------------------|
| Mobile device loss exposes notes/history | OS data protection, minimal cache, optional app lock decision |
| Tokens leak through app storage/logs | Platform secure storage, redaction, rotation and revoke flow |
| Untrusted EPUB/PDF/CBZ consumes resources | Input validation, decompression/size limits, bounded caches, fuzzing |
| Malicious document exploits native renderer | Track PDFium fixes, sandbox where available, prompt patch policy |
| Persisted file grants exceed need | Least-privilege picker grants, visible revoke/remove flow |
| Background sync surprises users | Opt-in, OS-compliant scheduling, network/battery controls and status |
| Store/OS backups copy sensitive database | Decide backup exclusion/encryption and document restore semantics |
| Cross-language/native boundary is unsafe | Narrow typed API, ownership rules, fuzz/error tests, no unwinding across FFI |

* Open Questions

- Is the validated product a companion, a full reader, or should mobile stop after
  the feasibility gate?
- Which first platform and minimum OS have available signing hardware/accounts
  and sufficient user demand?
- Does the Flutter vertical slice meet touch, accessibility, lifecycle,
  rendering, and packaging requirements on both mobile operating systems?
- Does EPUB mobile presentation consume a shared Rust scene or a shared semantic
  model laid out by Flutter?
- Which Dart/Rust binding approach passes both platform build and maintenance
  criteria?
- Which formats pass physical-device performance and binary-size budgets?
- Must the first mobile release transfer book files, or will users import them
  independently and associate by content ID?
- How should iOS security-scoped bookmarks or Android content URIs be refreshed,
  backed up, and represented in device-local storage?
- Is local database encryption or an app lock required by the threat model?
- What background-sync freshness can be promised under platform restrictions?
- How are desktop/mobile protocol rollouts coordinated when store review delays
  one client version?
