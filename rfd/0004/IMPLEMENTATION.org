#+TITLE: RFD 0004 implementation checklist
#+STARTUP: showall

Implements [[file:README.adoc][RFD 4: Cross-platform Flutter frontend]].

* Purpose

Replace the unreleased Iced presentation layer with one Flutter frontend for
desktop, phone, and tablet while retaining a platform-neutral Rust application
core.  Keep web viable through an explicit WASM or service adapter rather than
assuming native FFI works in a browser.

* Current baseline

- ~crates/shosai-app~ is an Iced desktop application that directly constructs
  core stores and documents and also owns reader sessions, EPUB pagination,
  caches, import orchestration, and platform integration.
- ~crates/shosai-core~ owns parsing, PDF/CBZ rendering, EPUB presentation,
  search, library persistence, reading state, and bookmarks, but its public API
  is not yet designed as a Dart bridge or browser boundary.
- RFD 6 Phase 0 has proved cross-format selection endpoints and bounded retained
  geometry with real Iced/PDFium/cosmic-text paths.  This evidence is sufficient
  to stop extending the Iced proof and use highlighting as the Flutter slice.
- The application is unreleased.  Development databases and internal APIs may
  be reset or replaced rather than carrying temporary compatibility machinery.

* Delivery rules

- Preserve behavior while extracting core responsibilities, then change the
  frontend.  Do not simultaneously redesign a domain contract and its Flutter
  presentation without executable core tests.
- Keep Iced runnable as a reference until Flutter satisfies the parity gate, but
  do not build complete new production features in both frontends.
- Move policy and domain behavior into core; leave widgets, gestures, navigation,
  lifecycle, and platform capabilities in Flutter adapters.
- Every native dependency must pass build, packaging, lifecycle, memory, and
  license gates on each claimed target.  Desktop success is not mobile evidence.
- Do not delay native delivery on web, push notifications, cloud sync, or all
  operating systems shipping simultaneously.
- Set a phase ~STATUS~ to ~IN-PROGRESS~ when its first task begins and ~DONE~
  only after every task and its ~Exit~ gate are satisfied.  Later phases may
  start early only where the dependency notes in the RFD permit overlap.

* M0 — Freeze the boundary and migration slice
:PROPERTIES:
:STATUS: IN-PROGRESS
:END:

- [ ] Approve RFD 4's single-frontend direction and record the initial supported
  desktop and mobile target matrix.
- [X] Use RFD 6 highlighting as the first cross-format Flutter vertical slice;
  treat its completed Iced Phase 0 as contract evidence, not production UI.
- [ ] Inventory every responsibility in ~shosai-app~ and classify it as core,
  Flutter presentation, platform adapter, temporary Iced reference, or obsolete.
- [ ] Choose the EPUB boundary: a Rust layout/scene consumed by Flutter or a
  semantic model laid out by Flutter.  Measure bridge volume, fidelity, selection,
  accessibility, relayout, and implementation duplication before deciding.
- [ ] Select a Dart/Rust bridge after proving Android, iOS, macOS, Windows, and
  Linux build integration, owned buffers, cancellation, error mapping, panic
  containment, and deterministic handle release.
- [ ] Record startup, memory, binary-size, render, selection-drag, and bridge
  latency budgets plus the accessibility acceptance matrix.

*Exit*: the core/frontend ownership table, bridge, EPUB rendering decision,
first target matrix, and highlighting slice are explicit enough to implement
without maintaining two production feature paths.

* M1 — Extract the Rust application core
:PROPERTIES:
:STATUS: IN-PROGRESS
:END:

- [ ] Move EPUB pagination and renderer-neutral geometry out of
  ~crates/shosai-app~, replacing ~iced::Size~ and widget types at the boundary.
- [ ] Extract reader-session policy: open/close, restore location, preferences,
  relayout anchors, and document replacement.
- [ ] Extract bounded rendered-page/resource caches, prefetch policy, and
  coalesced reading-state persistence without exposing Iced handles or tasks.
- [ ] Centralize format capabilities, import/open orchestration, and typed
  progress while leaving file pickers and UI progress presentation outside core.
- [X] Implement RFD 6's renderer-independent annotation domain, anchors,
  normalization, resolution states, and store before Flutter persistence work.
- [ ] Accept injected application-data locations and device-local file locators;
  stop requiring canonical desktop paths as portable record identity.
- [ ] Expose coarse async operations, owned DTOs, stable opaque handles, bounded
  byte buffers, typed errors, cancellation, and release through the bridge API.
- [ ] Feature-gate or adapt native-only dependencies so unsupported targets fail
  at build/configuration boundaries rather than through runtime surprises.

*Exit*: core tests exercise the application behavior without an Iced event loop;
no bridge-facing type contains Iced, Flutter, borrowed Rust, or durable viewport
coordinates.

* Verification and acceptance

- Core behavior and bridge contracts have deterministic Rust tests independent
  of Flutter and Iced.
- Flutter integration tests cover representative desktop, phone, and tablet
  states plus mouse, keyboard, touch, lifecycle, and restoration.
- Every claimed format and platform passes malformed/oversized fixtures, bounded
  memory behavior, native dependency loading, and package launch/open smoke tests.
- Accessibility validation covers screen readers, text scaling, contrast, touch
  targets, focus order, keyboard-only use, orientation, and non-color state.
- Paths and platform capabilities remain device-local; stable IDs and logical
  anchors survive relayout and synchronization boundaries.
- Credentials, note text, selected quotes, and reading history do not enter logs,
  crash diagnostics, notification payloads, or lock screens by default.

* Open questions

- Which bridge passes every native build and lifecycle gate with the smallest
  generated API and maintenance surface?
- Does Flutter paint a Rust EPUB scene or lay out a shared semantic model?
- Which Android/iOS platform ships first after physical-device evidence?
- Which native dependencies require platform adapters or replacement?
- Does web use local WASM/browser storage, a remote service, or remain deferred?
- Which notification use cases justify interruption, and which are better shown
  as in-app sync or activity state?
