= RFD 4 Cross-platform Flutter frontend

== Goal

Use one maintained presentation codebase for desktop, phone, and tablet while
retaining Shōsai's Rust document and application core. Preserve a credible web
path without claiming that native Rust dependencies already run in a browser.

== Proposal

Replace the unreleased Iced frontend with Flutter across Linux, macOS, Windows,
Android, and iOS. The existing Iced application remains an executable reference
during migration, not a second product frontend that must reach feature parity.
Delete it after the Flutter acceptance gate covers its required behavior.

[cols="1,1,2",options="header"]
|===
|Platform |Frontend |Direction

|Linux, macOS, Windows
|Flutter desktop
|Production desktop frontend after parity

|Android phones and tablets
|Flutter mobile
|Production target after physical-device validation

|iPhone and iPad
|Flutter mobile
|Production target after physical-device validation

|Web
|Flutter Web
|Feasibility target requiring WASM or service adapters
|===

The application has not been released. Internal Rust APIs, Dart bridge APIs, and
the development SQLite schema may change without compatibility wrappers or
dual-read periods. Once a release or synchronization wire format exists, its
declared compatibility contract applies normally.

== Rationale

Iced's desktop implementation proves important product behavior, but Iced does
not officially support Android or iOS. Owning mobile bootstrap, lifecycle,
packaging, software keyboards, accessibility, and platform services would turn
Shōsai into a mobile GUI framework maintainer.

Flutter contributes more than wrappers around native APIs. It provides one
widget, navigation, input, accessibility, localization, state-restoration, and
testing model across form factors; adaptive layouts; touch, mouse, keyboard,
and stylus input; hot reload; golden and integration tests; and a mature plugin
ecosystem. Those capabilities can be reused by every format reader and by sync,
annotation, notification, and settings experiences.

Keeping Iced on desktop and Flutter on mobile would preserve working code in the
short term but permanently duplicate reader interaction, accessibility, and UI
testing. Before release, replacing that duplication is cheaper than maintaining
two frontends indefinitely.

== Architecture

=== Rust application core

The Rust core owns document admission and parsing, resource limits, format
capabilities, stable locations, pagination and renderer-neutral layout where
portable, library operations, reader sessions, reading progress, bookmarks,
annotations, search, caching policy, stable content identity, SQLite storage,
and synchronization. Move code from `shosai-app` only when it is a coherent
platform-neutral responsibility; do not move widgets or event-loop state merely
to reduce the old crate's size.

Core APIs expose coarse commands, owned data transfer objects, opaque stable
handles, typed errors, bounded buffers, cancellation, and explicit resource
release. They do not expose Iced or Flutter types, borrowed Rust references,
framework messages, viewport pixels as durable locations, or per-glyph calls
across the bridge.

=== Flutter frontend and platform adapters

Flutter owns application navigation, responsive phone/tablet/desktop layouts,
reader gestures and shortcuts, overlays, accessibility semantics, localization,
safe areas, orientation, lifecycle, memory-pressure handling, file and document
providers, secure storage, deep links, notification delivery, signing, and
packaging. Platform plugins are replaceable adapters, not domain dependencies.

Native targets call Rust through a generated or hand-written Dart FFI bridge
selected by a measured spike. PDF rendering initially reuses Rust PDFium and
transfers bounded page or tile buffers. EPUB parsing, resource admission,
computed styles, stable offsets, embedded fonts, and MathML remain Rust-owned.
The spike decides the granularity of a Rust-laid-out renderer-neutral scene and
semantic representation that Flutter paints; it must not move document layout,
parsing, or resource security policy into Flutter.

Canonical paths, Android content URIs, iOS security-scoped URLs, and browser file
handles are device-local locators, never portable book identities. Flutter
supplies storage locations and file capabilities rather than asking Rust to
infer a desktop config directory.

=== Web boundary

Flutter Web does not make native Dart FFI, SQLx SQLite, PDFium loading, or direct
filesystem access browser-compatible. A web target must use the same conceptual
application API through either:

* a WASM build of the portable Rust subset plus browser storage, file, and PDF
  adapters; or
* a remote service implementing the application boundary.

The native release is not blocked on web. No core contract may unnecessarily
require a native path, thread, dynamic library, or SQLite connection when a
portable value or injected capability is sufficient.

=== Notifications

The core may emit a typed notification intent containing an event kind, opaque
record IDs, timing policy, and privacy-safe fallback text. Flutter adapters own
permission prompts, local scheduling, Android channels, Apple/Google push
registration, badges, actions, and deep-link routing. Reading reminders are the
first candidate and require no server. Remote push is added only for a concrete
server-originated event; push delivery is not part of the synchronization
protocol and never becomes required for convergence.

Lock-screen content defaults to generic text. Titles, note contents, reading
history, endpoint details, and credentials are excluded unless a user explicitly
chooses a more descriptive privacy setting.

== Feasibility and migration gate

Use RFD 6 highlighting as the first demanding cross-format Flutter vertical
slice after its renderer-neutral annotation model and store exist. The latest
Iced Phase 0 spike already proves PDF and EPUB selection endpoints; reproducing
the complete feature in Iced before migration would create disposable UI work.
The Flutter slice must prove:

* packaged Dart/Rust calls and deterministic resource release;
* SQLite create, reset/migrate, restart, and process-death recovery;
* PDF and EPUB opening, bounded rendering, selection hit testing, highlight
  overlays, persistence, and relayout;
* mouse, keyboard, and touch selection with one logical interaction contract;
* responsive desktop, phone, and tablet layouts;
* screen-reader semantics, focus order, text scaling, and non-color indication;
* cancellation, suspend/resume, rotation, memory pressure, and renderer recovery;
* reproducible debug and release builds with measured startup, memory, binary
  size, bridge latency, rendering latency, and drag latency.

Run the M2 slice on desktop and at least one physical Android or iOS device. One
mobile target may ship first, but evidence does not transfer between operating
systems: independently validate the other OS before claiming or packaging it as
supported. Web feasibility separately proves the chosen WASM or service boundary
and does not delay native migration.

After the gate, migrate the library shell and remaining reader behavior in
vertical slices. Keep Iced runnable for behavioral comparison, but add no new
production-only Iced feature unless it is needed to settle a core contract.

== Migration phases and tracking

Migration is tracked as dependency-ordered milestones rather than as one
frontend rewrite. Each milestone has an explicit exit gate in
link:IMPLEMENTATION.org[the implementation checklist]. A phase is complete only
when its exit gate is satisfied; checking individual tasks records progress but
does not waive the gate.

[cols="1,2,3",options="header"]
|===
|Phase |Outcome |Gate

|M0 — Boundary and slice
|Freeze core/frontend ownership, the bridge decision process, target matrix,
budgets, and highlighting as the first vertical slice.
|The boundary can be implemented without creating two production feature paths.

|M1 — Rust application core
|Extract renderer-neutral sessions, layout, caches, orchestration, persistence,
and coarse bridge contracts from the Iced application.
|Core behavior is independently tested and bridge-facing types contain no UI
framework or durable viewport state.

|M2 — Highlighting feasibility
|Build the smallest packaged Flutter/Rust application that opens EPUB and PDF
and completes selection, persistence, relayout, and accessibility end to end.
|The measured slice passes on desktop and at least one physical mobile platform;
otherwise reconsider the bridge, rendering boundary, or Flutter decision.

|M3 — Vertical product migration
|Replace the library shell and complete PDF, EPUB, and CBZ reader behavior in
reviewable vertical slices.
|Flutter passes the required desktop parity and regression matrix, making Iced
unnecessary for normal operation and testing.

|M4 — Platform services
|Add only product-required secure storage, deep links, sharing, background work,
local notifications, and eventually justified push notifications.
|Permission, lifecycle, privacy, duplicate-delivery, and stale-routing failures
are tested independently of synchronization correctness.

|M5 — Packaging and release
|Package, sign, and smoke-test each Flutter host with the Rust library, PDFium,
assets, manifests, and notices.
|Every claimed platform has an independently releasable artifact; then remove
the Iced application and its exclusive dependencies.

|M6 — Web feasibility
|Evaluate a browser-compatible core subset and adapters against a remote-service
boundary using opening, reading, search, and annotations.
|Record a separate web go/no-go decision without blocking or weakening native
delivery.
|===

M0 and M1 may overlap where an extraction is needed to measure a boundary. M2
is the Flutter go/no-go gate and precedes broad UI migration. M3 precedes final
Iced removal. M4 is demand-driven and need not block M3. M5 follows proven
product parity for each platform. M6 is intentionally independent and may run
in parallel once the portable application boundary is stable.

== Alternatives

Using Iced everywhere maximizes Rust UI sharing but requires unsupported mobile
platform ownership. Keeping Iced desktop plus Flutter mobile avoids an immediate
desktop rewrite but creates two long-lived interaction and accessibility stacks.
Separate SwiftUI and Android-native frontends maximize platform fidelity but add
two UI languages and still need another desktop frontend. Reconsider separate
native frontends only if the Flutter gate fails a required criterion.

== Dependencies and consequences

RFD 1's parser, resource-security, stable-location, and bounded-layout decisions
remain valid; its Iced implementation becomes migration evidence rather than the
future presentation boundary. RFD 2 format capabilities must drive one Flutter
reader shell. RFD 3 supplies portable identity and sync semantics independently
of notification delivery. RFD 5 must package Flutter hosts and the Rust native
library instead of assuming the current Cargo binary layout. RFD 6 supplies the
first cross-format interaction and persistence slice.

== Implementation

The dependency-ordered spike, extraction, migration, web, and packaging work is
