= RFD 4 Phase 2 evidence

Phase 2 implements and measures the packaged highlighting feasibility slice. It
does not convert simulator or automated evidence into a manual accessibility or
physical-lifecycle claim.

Android packages `libshosai_flutter_bridge.so` and the pinned
chromium/7999 PDFium arm64 artifact in the APK. PDFium is resolved by soname in
Android's package namespace rather than by interpreting the Android runtime
executable as a desktop installation path. Both downloaded PDFium archives and
the Rust bridge build are produced by the checked-in host build scripts. The APK
also carries the PDFium and third-party notices from that exact pinned archive.

iOS builds the bridge as a static library for arm64 devices and arm64/x86_64
simulators, then wraps and force-loads it with pinned PDFium 8046b in the
`shosai_flutter_bridge` CocoaPods framework. The reproducible wrapper verifies
the official Flutter 3.41.5 and PDFium archive checksums, uses writable SDK
artifacts, and removes inherited Nix SDK, compiler, deployment-target, and linker
settings before invoking Xcode. `make flutter-ios-simulator-debug`,
`flutter-ios-device-profile`, and `flutter-ios-device-release` all pass on the
Apple Silicon macOS builder; the latter two deliberately produce unsigned
artifacts. Because the 8046b distributor omits generated notices, the build
packages its MIT license plus a checksum-pinned conservative PDFium notice set
generated for the nearest available chromium/8044 branch and records that source
alongside the notices.

== Measurement protocol

Run:

----
make measure-flutter-m2 DEVICE=<flutter-device-id> OUTPUT=<evidence.json>
----

The profile harness performs five warmups and 50 measured samples. A synchronous
full-scene diagnostic round trip isolates generated bridge transfer and Dart DTO
materialization from Rust document extraction and layout. Selection timing uses
a directly pumped benchmark frame from synthetic pointer dispatch through UI
isolate overlay submission, so synchronous event handling is included while GPU
raster completion is excluded. A separate normal-frame pass records Flutter's
build and raster intervals for diagnosis. Static page content is behind a
repaint boundary and the dynamic painter draws only annotation and selection
overlays.

Native resource-cycle evidence discards five complete open/render/transfer/
release warmup cycles and records RSS after 20 further cycles. The
retained-growth decision compares the median of the first and final five-sample
windows with a 1 MiB tolerance for allocator and page-accounting noise. Raw
samples and the ordinary least-squares slope remain in each JSON record. The
logical resource checks additionally assert that document, raster, selection,
and cancellation handles release successfully. Separate rendered-reader flows
decode both PDF and EPUB; the EPUB flow selects, persists to the production
application-support database path, disposes, recreates the bridge, and reopens
the saved annotation. The repeated RSS value remains a native-cycle metric, not
a claim about repeated Flutter image decoding.

The Android profile APK is 47.4 MiB and the Linux profile bundle is 60 MiB. These
are build-artifact observations, not the RFD's installed-release-payload or
Flutter-over-native binary-size measurements. The fixture RSS is evidence for
the packaged feasibility slice, not the representative large-document ceiling.
Startup, installed release size, large-document steady RSS, full EPUB navigation
budgets, and comparison with the Iced reference therefore remain unclaimed.

== Accessibility, lifecycle, and visual evidence

Widget and controller regressions cover compact, medium, and expanded layouts;
safe areas and rotation; 200% text scaling; semantics and focus order; non-color
selection indication; lifecycle draining; process restoration; missing and
inaccessible locators; memory pressure; and renderer recovery. The physical
Pixel profile run verifies that the packaged PDF and EPUB bridge path and local
selection interaction execute on Android hardware. Its captured phone rendering
shows an aligned selected range and action surface without page-raster damage.
The final physical TalkBack run focuses the loaded PDF, announces the selection
action's purpose, activates it without a pointer drag, and exposes a selected-text
status plus individually announced, navigable Copy, Yellow, Green, Blue, Pink,
Purple, Add note, and Cancel controls. Android accessibility inspection confirms
that every control has an enabled tap action; each control measures 48 dp in its
shortest dimension. This proves screen-reader selection discovery and action
navigation, but not successful activation of every resulting operation.
The final iOS 26.5 iPhone 17 Pro and iPad Air simulator launches show the same
initial reader UI without a blank screen, native-library error, clipping,
corruption, or safe-area overlap. Because application startup awaits bridge
initialization, these launches exercise the packaged iOS framework load. The
immediately preceding branch lineage also completed the packaged PDF, EPUB,
selection, persistence, and metrics flow on both simulators; the final rerun was
blocked by an unrelated orphaned Flutter native-assets lock before launch. This
simulator evidence does not replace physical-device evidence. A signed copy of
the same iOS host installs and launches on the profile-covered iPhone 15 Pro Max
after the user explicitly trusts its development profile. Device process
inspection confirms that the VoiceOver services are active. With VoiceOver
enabled, on-device accessibility inspection traverses the initial reader in the
order `Shōsai` header, document-path label, path field, Open document button,
bridge instruction, and selection status. The spoken descriptions expose the
expected header and button traits, and the platform's sufficient-description,
contrast, hit-region, element-detection, text-clipping, trait, and dynamic-text
audits return no findings. Captures before and after foregrounding the same
process through Settings show the responsive host intact without clipping,
corruption, overlap, or safe-area intrusion, and post-resume traversal still
exposes every element. The inspection API does not prove preservation of the
user's exact VoiceOver focus.

These checks do not replace the rest of the required manual run. Broader TalkBack
explore-by-touch, successful screen-reader activation of Copy/highlight/note,
focus after an actual background/resume cycle, and platform
contrast/reduced-motion checks remain open on Android.
Gesture-driven VoiceOver traversal and rotor order, physical touch and document
selection/actions, orientation, large-text interaction, and exact user-focus
recovery remain open on Apple hardware. The signed iPhone host's
background/resume rendering and semantics availability are proven. Signed iPad
profile and release installation, launch, initial rendering, and semantics
availability are also proven, as are audible VoiceOver speech and visible focus,
but not its gesture-driven accessibility interactions. Missing files and revoked
document-provider capabilities also require a real provider rather than a
path-only fixture.

== Exit assessment

The packaged Flutter/Rust highlighting slice works end to end for PDF and EPUB
on Linux and one physical Android device, and its scoped performance gates pass.
That satisfies the M2 go/no-go evidence for continuing the Flutter migration.
It does not make iOS, Windows, or the deferred manual accessibility, lifecycle,
startup, large-document, and release-size checks pass; those remain explicit
target-specific work and may not be inferred from Android or simulator results.
